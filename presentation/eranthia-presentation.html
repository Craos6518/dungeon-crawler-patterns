El Proyecto

Arquitectura como artefacto vivo

Un proyecto académico que demuestra la implementación verificable de patrones de diseño en un dungeon crawler por turnos con flujo productivo en runtime.

El principio rector es que declarar un patrón implementado es insuficiente — cada patrón debe participar en el flujo real de GameRuntime → casos de uso → dominio, y debe estar validado por tests de integración que lo ejerciten desde la raíz.

El sistema soporta dos entornos de ejecución: WebView (JavaFX + WebEngine con HTML/CSS/JS) y consola, ambos sobre el mismo núcleo Java.

La campaña transcurre en cuatro biomas temáticos — Fuego, Hielo, Veneno y Oscuridad — con enemigos, loot y resistencias coherentes por tema.

🎯 Propósito Académico

Evidenciar patrones ejecutándose en flujo productivo con trazabilidad directa a código y pruebas. Permite defensa técnica sin depender de lectura completa del código.

⚙️ Flujo Principal

Menú → Selección de héroe → Exploración → Combate → Tesoro → Progresión por campaña (Poison → Ice → Fire → Dark).

🔒 Persistencia

Sistema de slots con serialización JSON completa. El Patrón Memento garantiza snapshots atómicos y rollback ante fallos. Schema versioning con v1.0.

📐 Contrato UI/Backend

El frontend HTML se comunica con Java mediante data-action / data-bind / alert-bridge. El núcleo corre independiente del shell visual.

Estructural
Composite
Inventario jerárquico

Maneja estructuras de contenedores anidados permitiendo operaciones uniformes sobre hojas y compuestos. El GameSessionMementoMapper serializa el árbol completo de forma recursiva, preservando jerarquías al guardar/cargar.

Decorator
Efectos de estado acumulables

Aplica efectos (veneno, quemadura, aturdimiento, fortaleza, guardia) de forma dinámica sin multiplicar condicionales. Máximo 3 stacks por efecto; los buffs se consumen tras uso.

Ancla: CombatStatusDecoratorPipeline · PoisonEffect · BurnEffect · StunEffect

Estructural
Facade
Subsistema de combate unificado

Expone un punto de entrada único para combate. GameSession.combat() retorna CombatFacade, que oculta Combat, CombatSystem, TurnManager y CombatStatusDecoratorPipeline.

Ancla: CombatFacade encapsula → Combat · CombatSystem · TurnManager

Comportamiento
Command
Encapsulación de acciones

Unifica la ejecución de acciones de combate e inventario. AttackCommand, DefendCommand, UseItemCommand y LevelUpCommand pasan por CommandInvoker con historial trazable.

Ancla: CommandInvoker · AttackCommand · UseItemCommand · LevelUpCommand
💾
Comportamiento
Memento
Persistencia y rollback

Serializa snapshots completos de sesión con schema versioning (v1.0). UseCaseTransactionSupport usa Memento para rollback atómico ante fallos. Detecta versiones incompatibles con SaveDataCorruptionException.

Ancla: GameMemento · GameSessionMementoMapper · GameCaretaker · RuntimeSaveSlotManager
👁️
Comportamiento
Observer
Eventos con aislamiento de sesión

Reacciona a eventos de juego sin acoplar emisores a consumidores. Cada sesión recibe su propio EventManager con observers locales; garantiza que eventos de la sesión A no se filtren en la B.

Ancla: EventManager · SessionEventFeedObserver · SessionEventCounterObserver
🗺️
Comportamiento
State
Flujo de pantallas y transiciones

GameStateContext es la fuente de verdad del flujo. Cada estado concreto gobierna qué acciones son válidas y qué transiciones están permitidas, eliminando strings hardcodeados de los use cases.

Ancla: GameStateContext → MenuState · CombatState · ExplorationState · GameOverState
🧠
Comportamiento
Strategy
IA adaptativa y estilos de combate

La IA enemiga selecciona estrategia según ratio de vida: Agresiva (>75%), Inteligente (50–75%), Defensiva (25–50%), Desesperada (<25%). El jugador cambia estilo en tiempo real consumiendo recurso.

Ancla: CombatSystem · AIStrategy → AggressiveStrategy · DefensiveStrategy · IntelligentStrategy

Arquitectura Runtime

El flujo canónico

Toda acción del jugador recorre el mismo pipeline, garantizando validación, trazabilidad y coherencia de estado.

01

UI envía comando JSON

El frontend HTML o la consola emite un payload con la acción del jugador. UiCommandDispatcher valida la estructura básica.

02

GameRuntime recibe y valida

RuntimePayloadValidator aplica validación estructural y tipada del comando. Si falla, retorna error sin mutar estado.

03

GameStateContext verifica permisos

GameSession.assertActionAllowed(action) delega en el estado activo. Solo las acciones válidas para el estado actual continúan.

04

Caso de uso ejecuta la mutación

El use case correspondiente modifica GameSession. UseCaseTransactionSupport toma snapshot previo para rollback ante excepción.

05

EventManager notifica observers

Los eventos del dominio se propagan al EventManager local de la sesión. SessionEventFeedObserver y SessionEventCounterObserver reaccionan sin acoplamiento.

06

GamePresenter construye ViewModel

GamePresenter mapea el estado interno a un GameViewModel JSON completo que la UI renderiza sin conocer el dominio. 

UI (HTML/Consola)
  │  JSON payload
  ▼
UiCommandDispatcher  →  estructura básica
  │
  ▼
GameRuntime  →  RuntimePayloadValidator  →  CampaignSessionCoordinator
  │
  ▼
GameSession  →  GameStateContext  →  GameState (activo)
  │                                    └── assertActionAllowed()
  ▼
Use Cases  →  CombatFacade  →  Combat  →  CombatSystem
             │               └── TurnManager
             │               └── CombatStatusDecoratorPipeline (Decorator)
             │
             ├── UseItemUseCase  →  CommandInvoker  →  UseItemCommand  →  Inventory
             ├── SaveGameUseCase  →  GameSessionMementoMapper  →  GameCaretaker
             └── EventManager.notificar(event)  →  SessionEventFeedObserver
  │
  ▼
GamePresenter  →  GameViewModel JSON  →  UI actualiza

Despliegue

Distribución nativa multiplataforma

Empaquetado con jpackage + jlink. JRE embebido: el jugador no necesita Java instalado.

🐧 Linux — Fedora primario

app-image / .deb / .rpm

Genera distribuciones nativas con JRE embebido. Validado en Fedora con app-image en target/packages/.

# Ejecutar juego ./play-gui.sh # Empaquetar ./package-linux.sh --type app-image ./package-linux.sh --type deb ./package-linux.sh --type rpm # Dependencias .deb/.rpm sudo dnf install dpkg rpm-build
🪟 Windows — Target secundario

Instalador .exe

Generado desde Windows con PowerShell. Requiere WiX Toolset en PATH. El .exe incluye JRE y JavaFX.

# Ejecutar en Windows .\play.bat # Empaquetar (desde Windows) .\package-windows.ps1 -Type exe .\package-windows.ps1 -Type app-image # Prerequisitos (JAVA_HOME/PATH + WiX) java -version where light
⚠ NOTA JPACKAGE — El parámetro --input debe listar JARs individuales o un directorio de JARs. Nunca pasar una fat JAR directamente como classpath o jpackage retornará error. Los scripts package-linux.sh y package-windows.ps1 ya contemplan esto correctamente.
